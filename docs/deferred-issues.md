# 暂缓问题清单

> 记录日期：2026-11-08。以下问题在 2026-11-08 全量审查中发现，经评估后**刻意暂缓**——
> 每一条都存在"改错比不改更糟"的风险，修复前需要构造验证样本或进行设计改动。
> 处理时请先阅读"修复前置条件"。

---

## 1. SyncPlay「暂停于 0」不跟随

- **位置**：`lib/pages/player/controller/player_syncplay_controller.dart:219-235`
- **现象**：多人共播时，远端成员把视频暂停在第 0 秒（开播即暂停、全员拖回片头暂停），
  本地不会跟着暂停，继续单播导致房间进度失步。
- **根因**：`position != 0` 守卫是故意写的——SyncPlay 协议入房时服务器会先发一个
  "暂停于 0"的握手初始包，不加判断会导致所有人一进房间就被错误暂停。
  现有写法无法区分"握手初始包"与"真有人在开头暂停"。
- **影响**：多人共播边缘场景的偶发失步。单人使用完全无感。
- **修复前置条件**：客户端状态机需要记录"握手完成/首次位置同步"的时机以区分两类消息。
  改错的后果是所有人无法正常入房，比现状严重。
- **验证方式**：双客户端（或 mock 服务器）共播测试：入房不误暂停 + 开头暂停能跟随。

## 2. Bangumi 收藏同步的两步提交原子性

- **位置**：`lib/services/sync/bangumi_sync_service.dart:142-150`
- **现象**：本地收藏变更分两步落盘——先写收藏主数据（`putCollectible`），再追加
  增量变更日志（`appendCollectChange`）。进程在两步之间被杀（崩溃/杀后台）时，
  变更日志缺失该条记录，多设备（远端）同步会漏掉这次修改，收藏状态静默漂移。
- **影响**：秒级窗口的进程死亡才触发；本地数据始终一致，只有跨设备收敛可能漂移。
- **修复前置条件**：调换两步顺序只是把问题镜像（日志有而数据没有）。正确修法需要
  一套"启动时校对数据与日志"的补偿机制，属于同步协议设计改动。
- **验证方式**：单测模拟两步之间抛异常 + 启动补偿回放，验证多端收敛。

## 3. Windows 系统代理检测的原生句柄注销缺失

- **位置**：`lib/services/network/system_proxy_service.dart:296-298`
- **现象**：win32 线程池等待（注册表监听）在启动失败路径会关闭事件句柄与回调，
  但不调用 `UnregisterWait`，理论上可能在原生层触发对已关闭 callable 的回调。
- **影响**：仅"代理检测初始化失败"这一条罕见路径；理论性问题，无已知复现。
- **修复前置条件**：FFI/原生层行为无法在本地自动化验证，盲改有启动崩溃风险。
  建议保持现状，待真实复现（崩溃日志指向该处）再修。
